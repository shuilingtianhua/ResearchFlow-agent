# 开发记录

本目录按时间记录 ResearchFlow Agent 每个可交付步骤的需求背景、实现过程、技术取舍和
验证证据。它回答的是“这一阶段为什么这样实现、实现到了什么程度、如何证明”，避免
代码演进后只剩结果而失去决策上下文。

## 与其他文档的关系

| 文档 | 主要问题 | 更新时机 |
| --- | --- | --- |
| `docs/PRD.md` | 为什么做、面向谁、需要什么能力 | 产品范围或验收标准变化 |
| `docs/ARCHITECTURE.md` | 系统长期边界和依赖方向是什么 | 稳定架构决策变化 |
| `docs/development/*.md` | 某一步如何实现、遇到什么问题、如何验证 | 每个可交付步骤 |

## 使用方式

1. 开始一个可交付步骤时，复制 `_TEMPLATE.md`，填写需求、背景、范围和方案。
2. 开发过程中同步记录关键决策、技术难点和被放弃的候选方案。
3. 完成时补齐代码映射、实际验证命令、结果、限制与下一步，并更新本索引。
4. 后续修复若改变原结论，应更新原记录的变更历史；形成新的行为闭环时新建记录。
5. 过期记录不删除，标记为“已归档”，并链接替代它的新记录。

## 写作原则

- 严格区分“已实现”“部分实现”“规划中”和“明确不支持”。
- 能力声明应链接到对应代码、测试、提交、PR 或实验产物。
- 只记录实际运行过的验证命令，不把计划执行写成已经通过。
- 说明选择某个方案的业务和工程原因，不只罗列代码修改。
- 实验记录额外保留环境、数据版本、参数、命令、指标和产物位置，确保可复现。

这些做法参考了 Sea-mult-agent 文档中“当前架构、产品流程、契约、安全边界、验收证据、
路线图和真实实验分开记录”的组织方式，但记录内容以 ResearchFlow Agent 当前代码为准。
