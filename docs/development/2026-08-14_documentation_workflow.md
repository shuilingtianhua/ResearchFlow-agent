## 1. 需求

为后续每个开发步骤建立强制、统一、可追踪的文档机制。记录不能只罗列修改文件，还要
解释业务原因、实现思路、技术难点、解决过程、验证证据、当前限制和后续工作，并参考
Sea-mult-agent 已有的丰富 docs 组织方式。

验收条件：

- 仓库级 Agent 规则明确要求同步编写开发记录。
- 提供可复用模板、索引和文档职责说明。
- 已完成的 M1 有一份内容完整、能够关联代码和测试的回溯记录。
- README 能让新参与者直接发现开发记录。

## 2. 业务背景与问题

ResearchFlow Agent 将分多个里程碑重构 Sea-mult-agent，并逐步引入存储、异步执行、模型、
沙箱和 AutoResearch。仅保留 PRD 和架构图，无法回答某个阶段为什么这样选择、遇到过哪些
失败、当时实际验证到什么程度。随着代码演进，缺少这些信息会导致重复踩坑，也容易把
未来路线图误写成现有能力。

因此，开发记录需要成为交付的一部分：PRD 管产品目标，架构文档管长期边界，按日期排列
的实施记录保存每一步的决策与证据。

## 3. 范围与非目标

### 本步骤范围

- 在根目录 `AGENTS.md` 中加入强制开发记录规则和完成标准。
- 建立开发记录索引、模板和写作原则。
- 回溯整理 M1 执行闭环记录。
- 在 README 中增加入口。
- 校验本地 Markdown 链接，并重新运行现有测试和静态检查。

### 非目标

- 不改变 M1 运行时代码、API 或状态语义。
- 不复制 Sea-mult-agent 的全部文档目录。
- 不在本步骤提交或推送 Git 变更。
- 不引入新的文档生成器或 CI 服务。

## 4. 当前基线与参考

变更前已有 [PRD](../PRD.md)、[架构设计](../ARCHITECTURE.md) 和根目录开发约定，但没有
按步骤记录的目录、模板或索引，M1 的实现依据和难点也分散在代码、测试和提交过程里。

本次从 Sea-mult-agent 的 docs 提炼并采用以下做法：

- 当前可运行架构与未来路线图分开描述。
- 文档写明最后验证日期、前置条件、部分能力和明确非承诺。
- 关键声明关联代码、测试或实验产物。
- 计划、实验和过期设计保留日期与历史，而不是覆盖掉上下文。

ResearchFlow Agent 没有照搬其目录，而是按当前规模收敛为 `docs/development/`，待真实实验
形成稳定数量后再考虑拆分 `plans/`、`experiments/` 和 `archive/`。

## 5. 方案与解决思路

采用“一条仓库规则、一个索引、一个模板、一事一记录”的轻量机制：

1. `AGENTS.md` 把开发记录纳入修改流程和完成标准，使后续 Agent 不能把它视为可选工作。
2. `docs/development/README.md` 解释文档分工、维护流程、状态词和全部记录入口。
3. `_TEMPLATE.md` 固定必填章节，减少每次重新决定结构的成本。
4. 日期文件保存单个可交付步骤；原结论变化时追加历史，不删除旧上下文。
5. 能力声明必须链接到代码、测试、提交、PR 或产物，验证表只写实际执行过的命令。

这个方案在当前阶段比引入文档站点更容易持续执行，也为后续按计划、实验和归档分类保留
了演进空间。

## 7. 技术难点与解决方案

### 7.1 避免文档重复和职责混乱

- 现象：需求背景可能同时出现在 PRD、架构文档和开发日志中，后续容易出现三个版本。
- 根因：没有定义每类文档负责回答的问题。
- 最终方案：明确 PRD 回答“为什么和做什么”，架构回答“稳定边界”，开发记录回答“这一
  步如何实现和证明”；记录以链接引用稳定文档，仅补充本步骤上下文。
- 选择理由：既保留决策过程，又不把开发日志变成第二份 PRD。

### 7.2 防止规划能力冒充现有能力

- 现象：参考项目包含大量完整设计，Python 重构尚未实现这些能力时很容易在文档中提前
  使用完成时态。
- 根因：架构目标、参考语义和当前代码证据没有分层。
- 最终方案：模板强制维护“已实现 / 部分实现 / 规划中 / 不支持”，并增加限制和非承诺
  章节；M1 记录逐项链接当前代码与测试。
- 选择理由：读者可以直接判断当前系统能做什么，而不需要从路线图反推完成度。

### 7.3 让历史验证与本次验证可区分

- 现象：M1 的完整构建证据来自原交付，本次只有文档变化；若混写，会让人误以为所有命令
  都在本次重新执行。
- 根因：实施记录缺少代码版本和最后验证时间语义。
- 最终方案：M1 表格明确证据对应提交 `e7e8fdc`；本记录单独列出本次实际执行的检查和
  未执行项。
- 选择理由：既保存历史交付证据，也不夸大本次验证范围。

## 9. 当前限制、风险与非承诺

- 规则依赖开发者和 Agent 执行，目前尚无 CI 检查新功能是否附带开发记录。
- 模板能提高一致性，但不能自动保证记录内容真实；仍需要代码评审核对证据。
- 当前记录数量较少，尚未拆分计划、实验和归档子目录。
- 本步骤没有提交或推送，远端 Draft PR 仍不包含这些文档变更。
